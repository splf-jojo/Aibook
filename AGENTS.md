# Работа над AIbook

## Цель продукта

AIbook — приложение для ведения записей с ИИ, интегрированным в многостраничный холст. Пользователь пишет, рисует и выделяет материал; ИИ анализирует заметки и размещает ответы, решения или объяснения прямо на холсте.

Чат и отправка изображений поддерживают этот сценарий. Не сводить конечный продукт к отдельному чат-боту или передаче PNG между устройствами. Корневой README описывает ранний MVP; актуальная цель зафиксирована в [ABOUT.md](ABOUT.md).

## Передача изменений через Git

- Обычный цикл: внести изменения → закоммитить относящиеся к задаче файлы → push в соответствующий репозиторий. Пользователь подтвердил оба адреса выше; рабочая ветка по умолчанию — `main`, если он не указал другую.
- **iPad-изменения пушить без предварительной сборки и тестов на Windows.** Не делать Xcode, симулятор, Swift toolchain или успешный build условием передачи кода.
- После push пользователь и помощник на Mac получают изменения, запускают build в Xcode и исправляют ошибки сборки. Не задерживать push попытками воспроизвести Apple-окружение на Windows.
- Не запускать обязательный полный набор проверок ради каждого коммита. Для правок документации сборка и тесты не нужны. Для бэкенда и web использовать локальный Docker, когда задача требует проверки поведения.
- Перед коммитом определить свои файлы по Git diff. Не включать посторонние незавершённые изменения и не стирать их ради чистого рабочего дерева. Не использовать force push или сброс чужих изменений.
- После push кратко сообщать репозиторий и коммит. Указывать только действительно выполненные проверки; не называть разбор Swift-синтаксиса успешной сборкой iPad.
- Если инструмент блокирует push, сообщить конкретную причину. Отсутствие Xcode само по себе не является причиной останавливать работу.

## Состав проекта

При создании и изменении интерфейсов читать и применять [промпт минималистичного дизайна](docs/UI_DESIGN_PROMPT.md). Оставлять только необходимые данные и действия; объяснения работы интерфейса и технические подробности переносить в документацию и чат.

- `backend/` — Python/FastAPI, PostgreSQL, JWT, хранение заметок и чатов, Qwen и API холста.
- `web/` — Next.js/React/TypeScript, редактор на Konva. При работе в этой папке учитывать её собственный `AGENTS.md`.
- `electron/` — Windows-клиент существующего сценария передачи изображений.
- Отдельный iPad-репозиторий — SwiftUI, PencilKit и SwiftData; проект `LuBoard.xcodeproj`, схема `LuceneBoard`.
- `API.md` — контракт между клиентами и бэкендом. `DEPLOYMENT.md` — развёртывание. В iPad-репозитории `CANVAS_ARCHITECTURE.md` описывает координаты, отрисовку, выделение и регрессии.

## Локальный Docker на Windows

Пользователь поднимает Docker Desktop на своём ноутбуке, чтобы проверить приложение до обновления сервера. Локальные контейнеры и контейнеры ECS — разные окружения, даже если у них одинаковые имена.

Полный стек в Docker из корня основного проекта, с уже настроенным локальным `.env.production`:

```powershell
docker compose --env-file .env.production -f docker-compose.production.yml up -d --build --wait --wait-timeout 120
docker compose --env-file .env.production -f docker-compose.production.yml ps
```

Проект Compose называется `aibook-production`: `web`, `api`, `postgres`, `caddy` и одноразовый `migrate`. Завершившийся с кодом 0 `migrate` — нормальное состояние. Локальный интерфейс доступен через Caddy на `http://localhost`, API — на `/api`, проверка доступности — `/health`.

`docker-compose.yml` без суффикса поднимает только PostgreSQL. Альтернативный dev-запуск через `start-all.cmd` запускает PostgreSQL в Docker, а API, web и Electron — отдельными локальными процессами. Не путать эти два режима.

Не перезаписывать существующие `.env` и `.env.production` при обычном запуске. Ключи Qwen, JWT, пароли, токены и архивы с секретами не добавлять в Git и не выводить в отчёт.

## Обновление сервера

На ECS только 2 ГБ RAM: **Docker-образы собирать на ноутбуке, на сервер передавать готовыми.** Для серверного образа явно использовать `--platform linux/amd64`, в том числе при сборке на Apple Silicon.

Порядок деплоя:

1. Собрать нужный образ локально; сохранить его через `docker image save` и передать через Workbench.
2. Сохранить предыдущий образ и серверные исходники для отката.
3. Загрузить образ через `docker load`. Обновить серверную копию исходников из того же коммита, сохранив существующую конфигурацию.
4. При наличии новых миграций применить их перед запуском API. Для обновления без миграций пересоздать только изменённый сервис с `--no-build --no-deps`.
5. Проверить healthcheck, необходимые маршруты и исправляемый сценарий. Git push сам по себе не обновляет ECS; деплой выполнять в рамках соответствующей задачи.

Пример перезапуска API после загрузки и назначения нового образа `aibook-api:local`:

```bash
cd /opt/aibook
docker compose --env-file .env.production -f docker-compose.production.yml up -d --no-build --no-deps --wait --wait-timeout 60 api
```

Не запускать сборку полного стека на ECS, не удалять volumes с PostgreSQL и не перезапускать остальные сервисы без необходимости. Команды экспорта образов, миграций и резервного копирования — в `DEPLOYMENT.md`.

## Холст и интеграция ИИ

- Исправлять причины ошибок координат, отрисовки и жестов; сохранять существующее поведение вне задачи.
- Бумага, штрихи, выделение и вставка должны использовать согласованные преобразования координат. Рост числа страниц не должен сдвигать объекты или обрывать текущий штрих.
- На iPad инструменты работают Apple Pencil. Палец используется для навигации и разрешённых действий интерфейса. Paste доступен пальцу и Pencil с Lasso; короткий штрих рисующего инструмента остаётся рисунком.
- Ключ провайдера ИИ остаётся на бэкенде. Клиенты обращаются к нему с авторизацией пользователя.
- Согласовывать клиентские запросы с `API.md` и фактически развёрнутым `/openapi.json`. Один успешный `/health` не доказывает наличие нового endpoint.
- Для чата используются создание `/api/ai/chats`, загрузка `/api/ai/chats/{chat_id}` и отправка `/api/ai/chats/{chat_id}/reply`. Не путать отсутствие маршрута с удалением конкретного чата и не терять из-за этого его историю.
- При изменении ответа ИИ на холсте учитывать контекст заметки, положение результата, сохранение и undo/redo. Существующие инструменты, перенос объектов и многостраничность должны продолжать работать.

## Общение и завершение задачи

Писать по-русски, коротко и по существу. Доводить согласованную работу до результата без повторных подтверждений уже разрешённых действий. В конце сообщать, что изменилось, что отправлено в Git, что реально проверено и что остаётся проверить на Mac. Не выдавать планируемые функции за уже реализованные.
